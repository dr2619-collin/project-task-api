# Module 07 Testing Public Behavior

Module 07 extends the Module 06 test suite with conformance, contract, and
negative tests. The focus moves from asking whether internal components work to
asking whether an API client can rely on the behavior the service publishes.

The API's public behavior includes its paths, HTTP methods, request fields,
response fields, data types, status codes, and documented error outcomes. The
generated OpenAPI document describes much of that agreement, while requests
against the running application verify that the implementation follows it.

## Test observable contracts

A public API is a contract between a service and its clients. Clients should
not need to know whether a response was produced by a particular service class,
repository method, or database query. They need stable, documented behavior at
the HTTP boundary.

Conformance tests therefore begin with what a client can observe:

- the paths and HTTP methods published by the API;
- request and response schemas, including required fields and types;
- successful status codes and response shapes; and
- documented failure statuses such as `404`, `409`, and `422`.

The tests do not assert private implementation details such as which repository
method ran or which SQL statement was generated. Those questions belong to the
unit and integration tests introduced in Module 06.

### Repository evidence

- `tests/conformance/test_openapi_contract.py`
- `docs/testing-conformance-contract.md`
- `/openapi.json`, generated by FastAPI from the application code

The OpenAPI tests use two complementary checks:

1. `openapi-spec-validator` confirms that the complete generated document is a
   structurally valid OpenAPI document.
2. Ordinary pytest assertions protect the specific paths, methods, schemas, and
   response statuses that this API promises to its consumers.

Structural validity alone is not enough. A document can be valid OpenAPI while
still accidentally omitting a required path or changing a response status that
an existing client depends on. Approved expectations make those important
course-level decisions explicit.

## Use negative testing to define failure behavior

Successful requests are only one part of an API contract. A reliable service
also defines what happens when a request is malformed, incomplete, refers to a
missing resource, or violates a business rule.

A negative test intentionally sends an invalid or disallowed request and passes
when the service rejects it predictably. Module 07 checks several boundaries:

| Request problem | Expected result | Main enforcing layer |
|---|---:|---|
| Missing or unknown JSON field | `422` | FastAPI and Pydantic |
| Blank or overlong Project name | `422` | Pydantic constraints |
| Non-integer resource ID | `422` | FastAPI typed path validation |
| Missing Project or Task | `404` | Service outcome translated by the router |
| Task references a missing Project | `404` | Application relationship rule |
| Project with Tasks is deleted | `409` | Application business rule |

The test should assert the stable part of the public contract. For example:

```python
assert response.status_code == 404
assert response.json()["detail"]
```

This verifies the status and that the response contains a non-empty `detail`
field without coupling the client test to wording that may change. Assert the
exact message only when that message is intentionally part of the published
contract.

### Repository evidence

- `tests/conformance/test_negative_requests.py`
- `app/schemas/` for request validation rules
- `app/services/` for missing-resource and relationship decisions
- `app/routers/` for translation of application outcomes into HTTP responses

## Keep contract tests at the public boundary

Conformance tests use `TestClient` to send HTTP-style requests through the
FastAPI application. They are not router-only unit tests and they do not start
Uvicorn or bind port `8000`.

```text
TestClient
    ↓
FastAPI router
    ↓
service
    ↓
repository → SQLAlchemy → PostgreSQL Testcontainer
```

The tests reuse the Module 06 database fixture, so each conformance test gets a
fresh database state and does not use the local development database. This
keeps the test at the public HTTP boundary while retaining realistic persistence
behavior underneath it.

Conformance tests complement the earlier test levels:

| Test level | Question answered |
|---|---|
| Unit | Does one rule work in isolation? |
| Integration | Do application layers work together with real infrastructure? |
| Conformance | Does the client-visible API follow its published contract? |

Do not repeat every successful workflow at every level. Choose the smallest
boundary that answers the question, then use conformance tests for the public
behavior that consumers depend on.

## Use schema-driven testing as a complement

Schemathesis reads the generated OpenAPI document, creates request cases from
the declared operations and constraints, sends them through `TestClient`, and
checks the responses against the corresponding operation schema.

Module 07 limits the generated demonstration to safe read-only operations:

```text
GET /health
GET /projects
GET /tasks
```

The flow is:

```text
OpenAPI document
    ↓
generated request cases
    ↓
real FastAPI response
    ↓
status and response validation
```

The lazy Schemathesis schema is connected to pytest through the
`openapi_schema` fixture. This preserves fixture ordering: the temporary
database is configured before the application and its OpenAPI document are
loaded.

Schema-driven testing is useful for exploring combinations that a developer
may not write by hand. It does not replace readable tests for intentional
business rules, such as returning `409` when a Project still has Tasks.

## Apply defense in depth for quality

Reliable behavior is protected by several overlapping mechanisms. Each layer
catches a different class of defect:

- Pydantic rejects malformed request data at the boundary.
- Services enforce application rules such as missing parents and protected
  deletions.
- Routers translate application outcomes into appropriate HTTP responses.
- Database constraints protect persisted relationships and data integrity.
- Unit tests isolate and verify individual decisions.
- Integration tests verify framework, ORM, repository, and database behavior
  together.
- Conformance tests verify the public contract and client-visible failures.

This overlap is deliberate. A schema cannot enforce every business rule, and a
database constraint cannot describe the complete HTTP contract. Defense in depth
means that a defect missed by one mechanism is more likely to be found by
another.

## Keep the contract and implementation aligned

Because this project uses a code-first framework, route decorators, type hints,
Pydantic schemas, and response declarations generate the OpenAPI document. A
change to those sources can change the public contract even when the application
still starts successfully.

When an endpoint changes, update the implementation, its documented OpenAPI
behavior, and the relevant conformance tests together. Review the change from a
client's perspective:

- Can an existing client still send the same request?
- Are required fields and response fields still present?
- Are status codes still meaningful and documented?
- Do invalid requests fail safely and predictably?

This practice prepares the project for later API evolution. Compatibility,
versioning, and deprecation are separate topics, but they depend on first
recognizing that the public behavior is a deliberate contract.
